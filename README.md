# Синхронизация Битрикс24 → Google Sheets

PHP-скрипт синхронизирует сделки из облачного Битрикс24 с Google Sheets. Сделки автоматически распределяются по листам `Август 2026`, `Сентябрь 2026`, `Октябрь 2026` и так далее. По умолчанию месяц определяется по дате создания сделки `createdTime`. Новая сделка добавляет строку, повторный запуск обновляет ту же строку.

Пошаговая установка на сервер, настройка доступов и разбор частых ошибок находятся в [INSTALL.md](INSTALL.md).

В синхронизацию попадают сделки выбранной воронки только в стадиях:

- Счет оплачен.
- Производство.
- Готовность.
- Документы.
- Сделка успешна.

Отбор выполняется по явным `STAGE_ID`, заданным в `BITRIX24_STAGE_IDS`. Названия стадий не используются, поэтому переименование стадии в интерфейсе Битрикс24 не изменяет состав выгрузки.

Скрипт использует универсальные методы `crm.item.*` для сделок (`entityTypeId = 2`), сам находит коды пользовательских полей по названиям и записывает значения через Google Sheets API v4.

Есть два запуска:

- `php bin/sync.php` — основная таблица руководителя со сделками всех менеджеров;
- `php bin/sync-managers.php` — отдельная Google-таблица для каждого менеджера, только с его сделками.

Оба варианта используют одинаковые поля и одинаковое помесячное распределение. Отсутствующие месячные листы и заголовки создаются автоматически.

## Определение месяца

По умолчанию лист выбирается по `createdTime` сделки:

```env
MONTH_SOURCE_FIELD=createdTime
```

Сделка с датой создания `2026-09-25` попадет на лист `Сентябрь 2026`. После установки помесячной версии обязательно один раз выполните `php bin/sync.php --full`; обычный инкрементальный запуск не перенесет старые неизмененные сделки из прежнего листа `Лист1`.

## Что именно обновляется

Правила находятся в `config/mapping.php`. Скрипт обновляет только перечисленные там управляемые столбцы. «Дельта», «комментарий если надо» и любые незнакомые столбцы остаются нетронутыми, поэтому формулы и ручные данные не стираются.

Следующий за данными 12-й столбец `L` используется для заголовка `Bitrix24 Deal ID`. Это стабильный ключ для upsert. При первом рабочем запуске заголовок создается автоматически. Если `L` уже занят, задайте другой номер в `TECHNICAL_ID_COLUMN`.

Видимый столбец `M` с заголовком `Ссылка на сделку в Битрикс24` также создается автоматически. В него записывается URL вида `https://example.bitrix24.ru/crm/deal/details/123/`. Если столбец `M` занят, укажите другой номер в `DEAL_LINK_COLUMN` или заранее добавьте столбец с таким заголовком в любом свободном месте.

Еще четыре видимых столбца создаются автоматически:

- `N` — `Дата создания сделки в Б24` из стандартного поля `createdTime`.
- `O` — `Дата перехода сделки в Успешно реализовано` — первая дата входа в стадию `WON` по истории движения сделки.
- `P` — `Тип сделки` из пользовательского поля `UF_CRM_1790575342`. Если это поле-список, записывается название выбранного значения.
- `Q` — `Дата выставлен счет` — первая дата входа в стадию `PREPAYMENT_INVOICE` по истории движения сделки.

Номера и заголовки этих столбцов можно изменить через `DEAL_CREATED_*`, `DEAL_WON_DATE_*`, `DEAL_TYPE_*` и `INVOICE_DATE_*` в `.env`. Если выбранный столбец уже занят, скрипт остановится и не перезапишет существующий заголовок. Все даты, включая `Дата принт`, передаются как строки без времени в формате `ДД.ММ.ГГГГ`, например `25.09.2026`.

Для существующих строк без технического ID предусмотрена безопасная миграция: если «Номер» совпал ровно с одной строкой, скрипт свяжет ее со сделкой. Дубликаты ID останавливают запуск вместо случайного обновления не той строки.

## Предварительные решения по неоднозначным столбцам

- «Дата принт» ← пользовательское поле «Срок выполнения заказа».
- «Менеджер» ← ответственный за сделку `assignedById`.
- «Сумма факт» ← «Себестоимость производства».
- «Дата создания сделки в Б24» ← стандартное поле `createdTime`.
- «Дата перехода сделки в Успешно реализовано» ← первая запись `WON` в истории стадий `crm.stagehistory.list`.
- «Дата выставлен счет» ← первая запись `PREPAYMENT_INVOICE` в истории стадий `crm.stagehistory.list`.
- «Тип сделки» ← пользовательское поле `UF_CRM_1790575342` (`ufCrm1790575342` в универсальном API).
- Сводное ТЗ собирается из материала, технологии, площади и производственного ТЗ.
- «Дельта» остается формулой Google Sheets.
- Комментарий остается ручным полем.

Если смысл отличается, измените соответствующую строку в `config/mapping.php` до первого полного запуска.

## Требования

- PHP 5.4 или новее.
- Расширения PHP: `curl`, `json`, `mbstring`, `openssl`.
- cURL/OpenSSL с поддержкой TLS 1.2 или новее — это требуется API Google и Битрикс24.
- Входящий вебхук Битрикс24 с правами чтения CRM и пользователей.
- Проект Google Cloud с включенным Google Sheets API и сервисным аккаунтом.

Код не использует синтаксис PHP 7/8, Composer или сторонние PHP-пакеты. Для совместимости с PHP 5.4 используются обычные свойства классов, `DateTime`, cURL и OpenSSL.

## Настройка Bitrix24

1. В Битрикс24 откройте «Разработчикам» → «Другое» → «Входящий вебхук».
2. Дайте вебхуку право чтения CRM. Для вывода имени ответственного также нужен доступ к пользователям.
3. Скопируйте URL вида `https://example.bitrix24.ru/rest/1/token` в `BITRIX24_WEBHOOK_BASE`.
4. Не добавляйте URL вебхука в Git: он является секретом.

В `BITRIX24_CATEGORY_ID` укажите ID нужной воронки. Для основной воронки используется `0`. Идентификаторы разрешенных стадий задаются в `BITRIX24_STAGE_IDS` через запятую. Для одной стадии можно использовать `BITRIX24_STAGE_ID`. Если задан список `BITRIX24_STAGE_IDS`, одиночное значение игнорируется.

Пример для дополнительной воронки с ID `7`:

```env
BITRIX24_CATEGORY_ID=7
BITRIX24_STAGE_IDS=C7:UC_PAID,C7:UC_PRODUCTION,C7:UC_READY,C7:UC_DOCUMENTS,C7:WON
```

Значения в примере условные. Используйте реальные `STAGE_ID` вашего портала.

## Настройка Google

1. Создайте проект Google Cloud и включите Google Sheets API.
2. Создайте сервисный аккаунт и JSON-ключ.
3. Сохраните ключ как `credentials/google-service-account.json`.
4. Откройте исходную Google-таблицу на редактирование для `client_email` из JSON-ключа.
5. Скопируйте ID таблицы из URL `https://docs.google.com/spreadsheets/d/ID/edit`.

## Запуск

```bash
cd /opt/bitrix24-google-sheets-sync
cp .env.example .env
mkdir -p credentials var
chmod 700 credentials
chmod 600 .env credentials/google-service-account.json
```

Заполните `.env`, затем выполните диагностику:

```bash
php bin/sync.php --diagnose
```

Диагностика проверяет оба API, заголовки листа и выводит пользовательские поля, которых пока нет в Битрикс24. Она ничего не записывает.

Проверьте план полного запуска без записи:

```bash
php bin/sync.php --full --dry-run
```

Первичная синхронизация:

```bash
php bin/sync.php --full
```

Последующие запуски выполняются инкрементально по `updatedTime`. Пятиминутное перекрытие защищает от пограничных изменений и не создает дублей:

```bash
php bin/sync.php
```

При каждом запуске найденная сделка обновляет свою существующую строку по `Bitrix24 Deal ID`; если строки еще нет, скрипт добавляет новую. Формулы и ручные столбцы не перезаписываются. Сделки, которые позже ушли из разрешенных стадий, автоматически из таблицы не удаляются.

Если для новой строки не хватает физического размера листа, скрипт автоматически добавляет блок из 1000 строк через Google Sheets API. Вручную расширять лист после достижения строки 1000, 2000 и далее не требуется.

## Cron

Откройте `crontab -e` у системного пользователя, которому доступны проект и JSON-ключ, и добавьте строку из `cron.example`, исправив путь:

```cron
*/5 * * * * cd /opt/bitrix24-google-sheets-sync && /usr/bin/php bin/sync.php >> var/cron.log 2>&1
```

Lock-файл не позволяет двум cron-процессам одновременно менять таблицу. Состояние последнего успешного запуска хранится в `var/state.json` и записывается только после успешного обновления Google Sheets.

Google ограничивает запись 60 запросами в минуту на пользователя проекта. Параметр `GOOGLE_WRITE_REQUEST_INTERVAL_MS=1200` ограничивает скрипт примерно 50 запросами в минуту, а `GOOGLE_WRITE_RATE_FILE=var/google-write-rate.lock` координирует этот темп между основным и менеджерским PHP-процессами. Cron-запуски желательно разнести по времени, чтобы синхронизация завершалась быстрее.

## Персональные таблицы менеджеров

Скопируйте пример конфигурации:

```bash
cp config/managers.php.example config/managers.php
```

Для каждого менеджера укажите его ID пользователя Битрикс24 и ID отдельной Google-таблицы:

```php
<?php
return array(
    101 => array(
        'name' => 'Иван Иванов',
        'spreadsheet_id' => 'GOOGLE_SPREADSHEET_ID_FOR_MANAGER_101',
    ),
    202 => array(
        'name' => 'Анна Петрова',
        'spreadsheet_id' => 'GOOGLE_SPREADSHEET_ID_FOR_MANAGER_202',
    ),
);
```

Ключ `101` или `202` — это значение стандартного поля сделки `assignedById`. Каждую таблицу откройте с правами редактора для `client_email` того же сервисного аккаунта Google.

Проверка без записи:

```bash
php bin/sync-managers.php --dry-run
```

Запуск одного менеджера:

```bash
php bin/sync-managers.php --manager-id=101
```

Полный запуск всех персональных таблиц:

```bash
php bin/sync-managers.php
```

Персональный запуск всегда читает полный актуальный набор сделок менеджера. Если сделка переназначена, ее строка очищается в таблице прежнего менеджера и появляется в таблице нового. Также очищаются сделки, которые больше не входят в разрешенные стадии.

Cron, например каждые 15 минут:

```cron
*/15 * * * * cd /opt/bitrix24-google-sheets-sync && /usr/bin/php bin/sync-managers.php >> var/cron-managers.log 2>&1
```

## Какие поля надо добавить в Битрикс24

Полное сопоставление новой структуры находится в `docs/field-matrix.md`.

Точно отсутствуют в переданном списке пользовательских полей:

- Материал заказа — строка или список.
- Технология — строка или список.
- Макет/ закупка/ доставка х1.5 — число или деньги.

Требуют решения по смыслу:

- Дата принт: сейчас используется «Срок выполнения заказа». Если даты различаются, нужно отдельное поле.
- Менеджер: используется стандартное поле ответственного `assignedById`.
- Дельта: формула зависит от вашего определения. Скрипт ее не перезаписывает.

Отдельное пользовательское поле для клиента не нужно: имя читается из контакта или компании, связанных со сделкой.
